# M002/S01 — Research

**Date:** 2026-03-16

## Summary

This slice adds TPoS auto-provisioning to the existing onboarding flow and surfaces merchant credentials. The three key risks identified in the roadmap — cross-extension HTTP calls, merchant credentials, and TPoS detection — are all solvable with existing patterns in the LNbits codebase.

The `create_user_account_no_ckeck` function returns a full `User` object with `wallets[0].adminkey` available immediately. The user's `id` is a UUID4 hex string that can be used for `login_usr` (`POST /api/v1/auth/usr`) when the `user-id-only` auth method is enabled (it is by default). This means the merchant login URL is simply `{base_url}/wallet?usr={user.id}` — no password generation needed. For the TPoS HTTP call, `httpx.AsyncClient` is already used extensively throughout LNbits, and `settings.lnbits_baseurl` (default `http://127.0.0.1:5000/`) provides the base URL for internal calls. TPoS installation can be detected via `get_installed_extension("tpos")` from `lnbits.core.crud.extensions`, which returns `None` if TPoS is not installed.

The implementation is straightforward: extend the models with new Optional fields, add a migration, modify the POST handler to conditionally create a TPoS terminal via HTTP, and return the enriched arrangement.

## Recommendation

**Approach:** Extend the existing `POST /api/v1/arrangements` handler with conditional TPoS provisioning via internal `httpx` call. Use `settings.lnbits_baseurl` for the base URL (not `request.base_url`, which can be unreliable behind reverse proxies). Detect TPoS installation via `get_installed_extension("tpos")` before attempting the HTTP call. Surface `user.id` as the merchant credential (login via `/wallet?usr={id}`).

**Why:** This follows existing LNbits patterns exactly — `httpx.AsyncClient` for HTTP calls, `settings.lnbits_baseurl` for URL construction, extension CRUD for registry checks. The soft-dependency approach (HTTP, not imports) keeps orangepiller installable without TPoS.

## Don't Hand-Roll

| Problem | Existing Solution | Why Use It |
|---------|------------------|------------|
| Internal HTTP calls | `httpx.AsyncClient` (already in deps, used in `notifications.py`, `extension_api.py`, `fiat_providers.py`) | Proven async HTTP client, already imported everywhere in LNbits core |
| TPoS detection | `get_installed_extension("tpos")` from `lnbits.core.crud.extensions` | Returns `InstallableExtension` or `None`; exact registry check, no guessing |
| Base URL for internal calls | `settings.lnbits_baseurl` (default `http://127.0.0.1:5000/`) | Already used in LNbits for self-referencing; `request.base_url` exists as a fallback but `settings` is more reliable behind proxies |
| Unique IDs | `urlsafe_short_hash()` from `lnbits.helpers` | Already used for `arrangement_id` in existing CRUD |
| Model-to-DB serialization | `db.insert()` uses `model.dict()` via `model_to_dict()` — fields with `no_database=True` are excluded | Add new fields to model, they auto-map to DB columns if migration adds them |

## Constraints

- **Pydantic v1 (1.10.x):** No `@computed_field`, no `model_dump()`. Use `.dict()` for serialization. New Optional fields must have defaults.
- **SQLite + PostgreSQL:** ALTER TABLE ADD COLUMN works on both but cannot add constraints in SQLite. Use `DEFAULT NULL` for new nullable columns.
- **`model_to_dict()` includes all fields from `.dict()`** unless `no_database=True`. Every field on `Arrangement` maps to a DB column — new fields need matching migration columns.
- **`tip_options` is a JSON string** in TPoS (e.g., `"[10, 15, 20]"`), not a list. Must serialize before sending to TPoS API.
- **TPoS `wallet` field is overwritten server-side** from the auth key — but our HTTP call authenticates with the merchant's adminkey, so TPoS will set `wallet` to the merchant's wallet. We should still pass it for clarity.
- **`create_user_extension` silently catches errors** (line 92 in `users.py`) — if TPoS is in `default_exts` but not installed, it logs an error but doesn't fail account creation. However, it's cleaner to check first and only add "tpos" when installed.
- **No new Python dependencies allowed.**

## Common Pitfalls

- **TPoS API authentication mismatch** — The `POST /tpos/api/v1/tposs` endpoint uses `require_admin_key`, meaning the `X-Api-Key` header must contain the merchant wallet's adminkey (not inkey). The endpoint extracts `wallet.id` from the key and sets it on the TPoS. Use `user.wallets[0].adminkey`.
- **`tip_options` serialization** — TPoS expects `tip_options` as a JSON-encoded string (`"[10, 15, 20]"`), not a Python list. Must `json.dumps()` the list before sending. The `CreateTposData` field type is `str`, default `"[]"`.
- **`settings.lnbits_baseurl` trailing slash** — Default is `"http://127.0.0.1:5000/"`. When constructing `/tpos/api/v1/tposs`, need to handle the trailing slash to avoid `//tpos/...`. Use `rstrip("/")` + path.
- **Pydantic v1 Optional field serialization** — `Optional[str] = None` fields serialize as `null` in `.dict()`. The `model_to_dict()` function passes `None` values to SQL. The migration must define columns as nullable (`TEXT DEFAULT NULL`).
- **`create_user_extension` error is logged but swallowed** — If "tpos" is added to `default_exts` and TPoS isn't installed, the account is still created but TPoS extension won't be enabled. Detection first is cleaner, but the fallback behavior is safe.
- **Race between account creation and TPoS HTTP call** — The merchant account must be fully created and wallet provisioned before the httpx call to TPoS. Since `create_user_account_no_ckeck` is `await`ed and returns the full User, this is guaranteed.

## Open Risks

- **`lnbits_baseurl` may not match the actual listening address in all deployments** — If the admin overrides it (e.g., to a public URL with HTTPS), the internal httpx call may fail or go through a reverse proxy unnecessarily. Mitigation: fallback to `request.base_url` if the `settings` call fails, or use `http://127.0.0.1:{port}` directly from settings.
- **TPoS API version stability** — We're coding against the current TPoS `POST /tpos/api/v1/tposs` contract. If TPoS releases a breaking change (new required fields, changed auth), the integration breaks silently. Mitigation: wrap in try/except, return arrangement with `tpos_id=None` and a warning.
- **User-id-only login may be disabled on some instances** — If the admin disables `user-id-only` auth method, the merchant can't use the `/wallet?usr={id}` login link. We surface the user ID regardless and note in the API response that login method availability depends on instance settings.
- **Multiple wallets edge case** — `user.wallets[0]` assumes a single wallet. `create_user_account_no_ckeck` creates exactly one wallet, so this is safe for the onboarding flow. But if the function changes, this could break.
